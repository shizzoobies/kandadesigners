## DEPLOY RUNBOOK (critical, read first)

**Git-triggered Cloudflare builds WORK** (fixed 2026-07-24, commit 45c0aa7): normal flow is build locally to verify, then `git push origin main` and Cloudflare builds + deploys automatically (~2-3 min). Verify at ka-performancefl.com (check page content, never just `/api/*`).

**Root cause was npm version skew, and it RECURS — proven again 2026-08-09.** The lockfile needs top-level entries for `@emnapi/core` + `@emnapi/runtime` (deps of platform-skipped wasm32 optionals of sharp/tailwind/rolldown). **npm 11's `npm install` silently strips them on Windows regardless of `NPM_VERSION=11` being set in CI** — that env var aligns the npm major but does NOT stop platform pruning. Installing `@astrojs/sitemap` dropped both entries (26 emnapi refs → 21) and the Cloudflare build failed; production kept serving the previous deploy. The fix that worked (commit 376019f): merge the two missing `node_modules/@emnapi/*` blocks back from the last good lockfile (`git show <good>:package-lock.json`), do NOT regenerate, then validate with a clean `npm ci --ignore-scripts` from a scratch dir before pushing. **So: after ANY local `npm install`, grep `package-lock.json` for `"node_modules/@emnapi/core"` — if gone, restore before pushing.** Best policy: avoid npm installs entirely; nothing on the current roadmap needs one.

## Process notes

**ROOT CAUSE FOUND AND FIXED 2026-07-30 — `src/pages/404.astro`.** The build emitted no `404.html`, so Cloudflare Pages answered *every* unmatched path with a **200 and an HTML body**. `public/_headers` stamps `immutable, max-age=31536000` on `/_astro/*` and `max-age=86400` on `/images/*`, so an asset requested during the rollout window (before that edge had it) got the 404 body stored **under the asset's own URL** with that TTL. This is what blanked Nicole's portrait, four of Bobbie's book pages, and finally took the entire site's CSS down when it landed on a stylesheet under the one-year immutable header. **Do not delete `src/pages/404.astro`** — with it present an unmatched path returns a real 404, which Cloudflare will not hold as a long-lived success.

The old mitigations below still apply as belt-and-braces, and the diagnosis technique is the important part to remember:

- **Diagnose FIRST:** compare plain vs cache-busted. `text/html` on the bare URL + `image/webp` (or `text/css`) on `?cb=123` = poisoned cache entry, NOT a missing file. The deploy is fine; do not panic-redeploy. `curl -sI` the bare URL and look for `cf-cache-status: HIT` with a long `Cache-Control` to confirm.
- **If it is already poisoned, only two things clear it:** Alex purging in the Cloudflare dashboard (Caching → Purge by URL, or purge everything — he did this to end the CSS outage and it worked immediately), or the referencing URL changing so the poisoned key is orphaned. The wrangler OAuth token is `zone (read)` only, so Claude cannot purge; ask Alex.
- **First probe safely:** always cache-bust (`?cb=$RANDOM`) when checking a freshly deployed asset. A cache-busted request cannot poison the real key.
- **Fix:** append a version query to the reference in source (`/images/art/x.webp?v=1`) — a new cache key, no file rename, bump the number if it recurs. Renaming the file works too but leaves `-v2` noise on disk. Purging via Cloudflare dashboard (Caching → Purge by URL) also works but needs Alex — the wrangler OAuth token only has `zone (read)`.
- **NEVER sweep bare asset URLs to "verify" a deploy.** This is how the CSS outage got re-triggered minutes after being purged: a post-deploy loop curled every `/_astro/*.css` the new HTML referenced, hit the rollout window, and pinned the 404 body under the fresh hash. Verifying is what broke it. Post-deploy, either probe with `?cb=$RANDOM` (a cache-busted key cannot poison the real one), or just load the page in a browser after a minute and read the console. With `404.astro` in place a missed asset now returns a real 404 so this should not recur, but do not go poking bare keys during a rollout regardless.
- **Prevention (cheap, do this by default):** ship brand-new asset paths with `?v=1` already on them. This has now bitten three times (Nicole's portrait, then 4 of Bobbie's 22 book pages) and it is a rollout race, not a bad file: some PoPs serve the new HTML before they have the new assets. Versioning up front costs nothing. Also give a deploy ~60s of quiet after the HTML flips before letting a browser load the page, since the browser requesting bare URLs is itself what caches the bad entry.

Also note `npx` breaks on this repo path (the `&` in "K & A"): run `node ./node_modules/astro/astro.js dev|build` instead.

**Git Bash mangles POSIX-looking values in command arguments, and it will send you chasing a phantom bug.** Testing the admin, `curl -d "...&returnTo=/clients/2"` arrived at the server as `returnTo=C:/Program Files/Git/clients/2`: MSYS2 path conversion rewrote it. It leaves values containing `://` alone, so the same test passed with an `https://` URL in the body and failed with a `javascript:` one, which looks exactly like a scheme-dependent code bug and is not. **Export `MSYS_NO_PATHCONV=1` before any curl whose body or query contains a bare `/path`**, or use PowerShell. Related trap in the same session: a raw `&` inside a urlencoded body (`source=Referral from PB&J`) silently truncates the value, so use `--data-urlencode` per field. Both were harness faults, not app faults, and both cost real time to isolate.

Astro also **excludes `_`-prefixed files in `src/pages` from routing**, so a scratch debug endpoint named `__echo.js` 404s and looks like a broken dev server.

**Stopping a background dev server does NOT reap wrangler's children on Windows.** Two days after the admin build, an `astro dev` on 4321 and a whole `wrangler pages dev` tree on 8788 (parent, cli child, and an orphaned `workerd.exe`) were still alive and still holding the `SONGS_DB` binding, despite the shells having been stopped. Match on the command line rather than the process name: plenty of unrelated `node.exe` processes belong to other sessions and the editor, and killing those breaks things.
